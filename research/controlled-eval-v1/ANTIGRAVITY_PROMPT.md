1. Questions and claims to test
Q1. With identical schema-grounded messages, token caps, sampling settings and requested thinking settings, how do prompt_only, native_original and native_projected differ in request acceptance, completion, original-schema validity, task agreement, output length and end-to-end latency?
Q2. Does provider-facing projection help in the declared supported subset while preserving original validation? Which transformations ran, which were rejected and which constraints remain? Projection is a separate experimental factor. This is not a comparison of 'schema versus no schema': all three modes receive the same schema in their messages; only the native constraint argument differs.
Q3. Which failures are ordinary schema-authoring gaps addressed by trusted const/enum/bounds, which require deterministic relationships, which depend on runtime evidence, and which still require interpreting the source?
Q4. For naturally generated detectable failures, does actionable feedback improve recovery relative to generic and raw-validator feedback? Compare budgets of zero, one and two repairs, with identical saved initial outputs. Measure remaining incorrect answers, unwanted changes to initially correct fields and added latency/tokens/requests.
Q5. What can these experiments actually establish about reusable rules or a future vocabulary? Application rules are not implemented JSON Schema custom vocabularies. Synthetic case frequencies are not company demand or proof that a small rule set covers 80% of real needs.
Do not assume schemas always reduce latency, that every unsupported keyword must yield a violation, that a passing output proves decoder enforcement, or that one retry almost always succeeds. Treat these as questions.
